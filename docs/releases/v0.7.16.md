# Kyrei v0.7.16 — 🛡️ the agent can no longer talk itself into changing itself

v0.7.15 gave Kyrei a way to be measured. This release uses it: three things that
were decided by an opinion are now decided by evidence, and one measurement that
was quietly wrong is now right.

Four research swarms ran against the current state of the art in promotion
statistics, performance, memory and the competitive field. As last time, the most
useful results were **negative** — several plausible builds turned out to be
refuted, and one recommendation was rejected after checking it against the code.

## 🛡️ A model may veto a self-modification. It may never approve one.

The only thing between a harvested candidate and a real write to disk was a
single model call scoring its **own** confidence, admitted at 0.5. The module's
own comment said it plainly: *"a single model call with no baseline and no
replay, so the score is the only signal."*

That design is refuted, not merely thin. Measured on a memory-poisoning
benchmark, an LLM trust-scorer admitted 82 entries of which **54 were malicious
and scored a perfect 1.0**. Judges carry a false-**pass** bias, and a false pass
here is a self-modification that ships.

The decision is inverted. Approval now comes from deterministic, checkable
properties of the candidate — a new `core/evolution-admit.js` — and the model is
advisory with veto power only:

| | outcome |
|---|---|
| inadmissible | rejected, whatever the model said |
| model vetoes | rejected, however strong the evidence |
| model approves | approved **only if** admissible |
| model unreachable | **rejected**, not approved |

The last row matters: a model that cannot be reached now blocks
self-modification instead of waving it through — the same fail-closed reasoning
as `verify-before-done`.

**Evidence is checked, not narrative.** A "repeated failure pattern" must cite
occurrences *and* samples; a count with no samples is an assertion about
evidence, not evidence. An unrecognised proposal shape scores zero, so new
shapes must be admitted consciously. Secrets are re-checked at this gate because
it is the last one before the executor writes.

An inadmissible candidate is now rejected **without a model call** — asking
cannot change the outcome, it costs money, and it would put a malformed proposal
into a prompt for no reason.

### 🎭 The `risk` field carried no information

All three harvested candidate shapes hardcoded `risk: "low"`, so **every gate
keyed on `risk === "low"` was vacuous** — including the canary check in the
gateway and the review gate above.

Risk is now a property of what the candidate **writes**. A reliability hint is a
note in the journal and stays low. A skill draft creates a file the agent will
load and act on, so it is medium and goes to a human. That is also where the
evidence points: machine-generated policy text derived from an agent's own
trajectories has not been shown to beat fixed prompting, and nothing here can
measure whether it did.

## 📊 The prompt cache is measured, and priced correctly

The provider already reports how many prompt tokens were **written** into its
cache. The bridge dropped that number and kept only reads.

That gap is not cosmetic. **Reads alone cannot distinguish a working cache from
one rewritten on every step** — both show reads near zero. The second is what a
cache invalidated mid-turn actually does, and it is the expensive failure.
Kyrei now records reads, writes, uncached tokens and a hit rate.

**Cost was wrong in both directions.** Every input token was billed at the full
rate, so a cached prefix — which bills at a **tenth** — was overstated by up to
10×, and a cache write, which bills at **1.25×**, was understated. The ledger
therefore could not answer the one question it would be most useful for: did a
caching change help.

### 🕳️ A metric can be recorded correctly and still never arrive

The gateway's metrics whitelist silently drops anything not named in it, which
is exactly what happened to the patch-outcome counters added in v0.7.15: the
engine recorded them and `/api/usage` never saw them. Both the patch and cache
counters are now allowed through, with the label maps sanitised rather than
trusted — that object is serialised into an API response.

## 🧩 `~/.claude/skills` is read, and duplicates stop looking like a bug

`SKILL.md` became the cross-vendor format — Copilot, Devin, Junie, Zed,
OpenHands and Amp all read it, several citing the open spec — and a user
arriving with an existing library keeps it in `~/.claude/skills`. Kyrei read its
own root, the workspace root, custom roots and `~/.kiro/skills`, but not that
one. It is now discovered the same way Kiro is: **read-only**, never rewritten
by the curator or the evolution executor.

**The naive version of this would have been harmful, and measuring said so.** Of
55 skills in `~/.claude/skills` on a real machine, **53 were already present** in
Kyrei's own root, so the catalog went from 97 entries to 152. Discovery
deduplicates by *file path*, which cannot see that two roots hold the same skill
in different directories.

The runtime path was never at risk — `runtimeSkills` already collapses by name.
Verified on real data: **58 skills injected, zero duplicate names, before and
after.** Only the listing was broken.

So the fix is not to hide sources. Discovery now **marks** the losers and the
catalog dims them with a "shadowed" badge. Same data: 152 entries, **58 active —
matching the runtime catalog exactly** — and 94 shadowed, of which **41 came
from Kiro and were already duplicates before this change**, with no explanation
anywhere in the UI. Two genuinely new skills became available.

Two smaller things this surfaced:

- The provenance precedence table had no entry for the new root, and a missing
  entry subtracts to `NaN` — which stops the comparator being a total order and
  makes which copy "wins" implementation-defined, including, possibly, the
  foreign one.
- `provenanceLabel` ends in `default: "Global"`, so a read-only foreign root
  would have been displayed as Kyrei's own. It now has its own label in both
  locales.

## 🧭 What the research said not to build

- **Session sharing — retracted.** Amp is the cautionary tale: workspace members
  default to workspace-wide visibility, *private* threads stay visible to
  workspace admins, and Amp ended public threads proactively because as models
  improved they pulled more files into context, making threads *"increasingly
  difficult to review for sensitive file snippets."* For an agent whose
  distinguishing feature is redaction on every channel, that is importing the
  exact risk a competitor retreated from.
- **A replay gate on the existing eval suite.** The suite scripts the model's
  decisions and passes no `system` field and no skills, so a prompt-profile or
  skill edit cannot change one bit of its output. A gate built on it would
  always report "no regression" — a rubber stamp in a statistics costume.
- **Detecting *improvement* on 18 tasks.** It needs ≥5 same-direction flips with
  zero counter-flips. That is not a tuning problem; the suite is a
  never-regress gate, and it is treated as one.

## 🔎 One recommendation checked and rejected

The research advised moving the eval suite out of the executor's writable
surface, citing a self-modifying agent that removed the markers detecting its own
hallucination *despite explicit instruction not to*.

Checked: it does not apply. Skill writes are constrained to
`^skill_[a-f0-9]{24}$` and `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` — no slashes, no
dots, no traversal — and reserved profile ids are refused. The executor cannot
reach `tests/eval/` by construction.

## 📌 Known, and deliberately not fixed here

- **The canary transition is still the application.** It is gated on a mode flag
  and a risk check — which is no longer vacuous, but there is still no
  measurement window and no automatic rollback.
- **Automatic recall is still BM25-only** and consults neither the vector store
  the project ships nor the sufficiency gate its explicit memory tools use.
- **The Atlas still has no tool surface.** The agent builds the graph and never
  queries it.
- **`list()` still shows 94 shadowed rows** on a machine with three overlapping
  skill roots. They are now labelled rather than mysterious; collapsing them
  behind a toggle is a UI change, not a correctness one.
