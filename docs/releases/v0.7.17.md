# Kyrei v0.7.17 — 🩹 a truncated response can no longer destroy a file

One fix. It is a data-loss bug, it was reproducible, and it had no guard of any
kind.

## 🩹 What was broken

When a provider stops a response because it hit the **output token limit**, the
assistant message can still carry tool calls — and their arguments were cut off
mid-stream. The SDK finalises whatever arrived, so a call whose JSON happens to
close early **parses, validates against the schema, and executes**.

Reproduced against Kyrei's own tool loop:

```
before:  a.txt = "ORIGINAL\n"
model:   write_file {"path":"a.txt","content":"TRUNCA"}   ← cut off mid-stream
         finish, reason = length
after:   a.txt = "TRUNCA"
```

The model had been cut off mid-sentence. The write looked complete, passed every
check, and destroyed the file's contents.

Nothing in the engine looked at the finish reason except a single check for
`"error"`, so this class of failure was entirely unguarded. A long file rewrite
that runs out of output budget is exactly the situation where it fires — which
is to say, on the largest edits, the ones most expensive to lose.

## 🔒 What changed

A middleware watches the model stream and raises a flag when the length stop
arrives. That signal lands **before** the SDK executes the tool calls it
collected, so `executeGuarded` can refuse on it.

The refusal travels back through the **normal tool-result path**:

> Tool call not executed: the response hit the output token limit, so this
> call's arguments may be silently truncated and acting on them could corrupt a
> file. Re-issue the call with complete arguments, splitting the work into
> smaller steps if needed.

That wording is deliberate. A call that simply vanished would leave the model
with no idea why, and it would try again identically. Told what happened, it
splits the work and continues — a normal recovery, where a half-written file is
not.

Text keeps streaming untouched; only tool execution is gated.

**Both stop-reason shapes are read** — a bare `"length"` and the
`{ unified, raw }` object form — because getting this wrong fails **open**: the
guard would silently never fire, and the corruption would look like a model
mistake rather than a harness one.

## 🦷 Proven to fail, not just to be green

Removing the flag assignment turns exactly two of the three new tests red, and a
normally finished call still writes. The guard is targeted, not a blanket
refusal on anything unusual.

## 🔭 How it was found

By studying [`earendil-works/pi`](https://github.com/earendil-works/pi) — the
engine underneath `eggent-ai/eggent`, which turned out to be a UI shell rather
than an agent of its own. Pi handles this case explicitly, with a comment naming
exactly the failure mode: streamed tool-call arguments are finalised by a
best-effort parser, so a truncated message can yield calls whose arguments
validate and are silently incomplete.

Reading that was enough to suspect it. Reproducing it against our own loop is
what made it a bug report instead of a hunch.

## 🧰 Also

`run.test.ts` mocks the `ai` module and had to declare the new export the engine
depends on. The wrapper is the identity there; its real behaviour is covered
against the real SDK in `provider/truncation-guard.test.ts`.

## 📌 Found in the same study, not fixed here

Two further findings from the same engine, both confirmed absent in Kyrei and
both deferred rather than rushed into a data-loss patch:

- **Context-overflow detection has three shapes, and we handle one.** The
  missing two are *silent* overflow — a `200 OK` whose reported usage already
  exceeds the window — and *length-stop* overflow, where the server truncated
  the input to fit and left no room for output. Both are currently
  indistinguishable from "the model just stopped."
- **Parallel tool calls are not serialised per file.** Two edits to the same
  path in one step can interleave read-modify-write and lose one of them. Two
  independent reviews flagged this.

And one capability gap, from the product layer above that engine: binary and
office documents are rejected outright (`document_binary_unsupported`), so PDFs,
DOCX and scans cannot enter memory at all.
